# 用户状态设置与展示（v26.07.0 -> v26.08.4）

## 生产级长程任务定义

### 任务定位
本任务不是在设置页添加一个静态入口，而是把 Matrix 用户状态能力作为一个端到端产品功能迁移到 ArkTS 客户端。实现需要贯通 homeserver capability 探测、当前用户资料、状态编辑器、状态更新 side effect、远端成员状态同步、房间列表摘要、用户资料页、时间线发送者区域和通话状态自动化。候选实现只有在这些状态源互相一致、失败路径可恢复、且不破坏现有设置/房间/时间线行为时，才算完成。

### 版本边界
- base: Android `v26.07.0`，用户状态不作为完整可用功能暴露；对应 ArkTS base 必须缺少 final 语义。
- final: Android `v26.08.4`，包含用户状态能力启用、feature flag 移除、`MatrixClient.isUserStatusSupported`、用户状态展示模型和时间线只展示 emoji 的行为。
- ArkTS 目标必须使用 SDK 23，并保持与 Android final 的功能边界一致；不得额外加入 Android final 没有的状态类型、设置项或社交功能。

### 生产级交付要求
- 能力探测必须是运行时状态，而不是编译期常量；失败、unsupported 和 supported-empty 三种状态要有不同 UI 收敛。
- 状态编辑器必须支持预设状态、自定义 emoji/text、取消、保存、清除、保存失败回滚和重复提交保护。
- 当前用户状态、DM 成员状态和时间线发送者状态必须使用同一语义模型，避免设置页、房间列表和资料页显示不一致。
- 时间线只允许显示状态 emoji，不允许泄露完整状态文本到消息正文或发送者行。
- 通话状态如果被映射为用户状态，必须能在通话结束后恢复或清除，不得覆盖用户手动设置的持久状态。

### 非目标与回归约束
- 不改动 Android production source；Android 只允许使用 debug/test harness 注入状态。
- 不改变账号、安全、隐私、通知、房间列表排序、未读数、时间线消息顺序和消息操作菜单。
- 不依赖 `state_test_result`、版本号、feature flag 字符串或单一 marker 判定通过。

### 验收口径
每个 testcase 必须能通过状态向量驱动到具体 UI：capability、状态 payload、编辑器模式、保存 action、目标 surface 和远端成员状态至少有一项参与断言。base/final 极性要求为 Android base fail、ArkTS base fail、Android final pass、ArkTS final pass；任何只让 `feature_available=true` 但没有渲染对应入口、badge、错误态或 transition 的实现应被判为失败。

## 场景一

### 场景概述

用户可以在设置页管理自己的 Matrix 用户状态。相比 base 版本，final 版本需要补齐用户状态入口、编辑流程、保存/清除状态逻辑，并在服务端不支持用户状态能力时安全降级。该需求对应原仓库 release note 中 “Enable user status feature and hide status text in the timeline” 以及相关用户状态 feature flag 移除、`MatrixClient.isUserStatusSupported`、状态预览和展示组件调整等变更。

### 场景逻辑步骤

- 1. 用户进入登录后的设置页。
- 2. 当 homeserver 支持用户状态能力时，设置页显示“我的状态”相关入口；当能力不支持或状态数据不可用时，该入口应隐藏或显示为空状态，不应影响其它设置项。
- 3. 用户点击状态入口后，进入用户状态编辑界面或弹层。
- 4. 编辑界面展示可选的预设状态，并允许用户输入或选择自定义 emoji/text 状态。
- 5. 用户保存状态时，客户端调用用户状态更新逻辑，并在保存期间显示明确的加载状态。
- 6. 保存成功后，设置页展示最新状态；保存失败时保留原状态并显示错误提示或可重试状态。
- 7. 用户选择清除状态时，客户端移除当前用户状态，设置页恢复为无状态展示。
- 8. 状态设置流程不得改变账号、隐私、安全、通知等其它设置项的原有行为。

## 场景二

### 场景概述

用户状态需要被房间列表、DM 信息和用户资料等界面消费。base 版本中这些界面没有用户状态展示；final 版本需要在可用数据存在时展示状态，并避免在群聊或无状态用户上凭空生成内容。

### 场景逻辑步骤

- 1. 用户在设置页设置自己的用户状态后返回主页。
- 2. 主页顶部与账号相关的头像区域应能展示当前用户状态的 emoji 标识。
- 3. 房间列表加载 DM 和群聊摘要。
- 4. 对于 DM 房间，如果对方成员存在用户状态，则房间摘要行展示该状态对应的 emoji 或状态提示。
- 5. 对于群聊房间、无状态成员或状态数据未加载完成的房间，不显示虚假的用户状态。
- 6. 用户进入成员资料页或房间顶部区域时，界面使用同一份展示状态数据，避免不同页面出现互相矛盾的状态。
- 7. 当状态更新、清除或同步刷新后，相关 UI 自动刷新。
- 8. 房间列表原有未读数、置顶、静音、头像、最后一条消息等展示逻辑保持不变。

## 场景三

### 场景概述

时间线中的发送者状态展示需要与 final 版本保持一致：只渲染 emoji，不展示完整状态文本。此变更需要兼容普通文本、图片、媒体消息和已有时间线布局，不能破坏消息顺序、发送者信息和事件操作。

### 场景逻辑步骤

- 1. 用户进入包含多名发送者的房间时间线。
- 2. 当某个发送者存在用户状态时，其消息发送者区域展示状态 emoji。
- 3. 时间线中不直接展示用户状态文本，避免占用消息正文区域。
- 4. 当发送者没有状态、状态过期或服务端不支持用户状态时，时间线按 base 版本方式展示发送者信息。
- 5. 普通文本消息、单媒体消息、回复、反应和日期分隔符继续按原顺序渲染。
- 6. 用户状态展示不应影响消息长按菜单、回复、转发、详情等已有操作。
- 7. 如果应用支持通话期间自动状态，进入通话时可自动设置通话状态；通话结束后恢复或清除对应状态。
- 8. 自动状态能力失败时不应阻塞房间时间线和通话流程。
